建 Wiki 前的設計

先提出「HTTP 快取入門」、初學者讀者與海報情境，並請使用者選擇是否採用。初版依自由選題授權執行，之後收到使用者回覆「採用這個範圍」。本次在確認後重新擷取五篇來源、更新 Wiki、檢查並產生 HTML。實際對話節錄與執行順序收在 ZIP 內的 workflow/scope.md。

五篇資料逐篇擷取，再彙整成五個互相連結的概念條目。遇到近似說法時先分辨情境，例如一般再次請求和手動重新整理可能走不同路徑。儲存規則以 RFC 為基準，操作以 Chrome 官方文件為基準。

ZIP 中的 raw/ 保存實際擷取時間、最終 URL、回應標頭及 SHA-256，raw/captures/ 保存五份完整 HTML 回應。來源及概念頁在 wiki/，維護方式在 AGENTS.md。依 Karpathy 的來源、Wiki 與維護規則三層架構整理。Karpathy · LLM Wiki

Graph 與退回路徑

由「製作給初學者的 HTTP 快取簡報」觸發。每次先讀 Wiki，為大綱中的教學問題配對概念和證據，再撰寫、檢查並渲染。

  1. 01 擷取資料讀原文，保存定位與擷取指紋
  2. 02 整理 Wiki寫來源摘要、概念、索引及日誌
  3. 03 查詢 Wiki用教學問題找概念、選證據
  4. 04 檢查大綱條件逐頁確認來源與示例前提
  5. 05 產生逐頁稿用入選證據寫內容、例子和練習
  6. 06 檢查內容核對用詞、條件和逐頁引用
  7. 07 渲染 HTML讀核對後的稿件、產生頁面
  8. 08 瀏覽驗收測試畫面、翻頁、測驗與連結
何時重跑退回哪裡修正原因
每納入一篇來源擷取 → Wiki → 檢查段落定位來源有自己的擷取紀錄和摘要，概念可以合併引用多篇資料。
大綱缺直接證據回查詢，必要時回擷取在起稿前確認說法有足夠的 Wiki 支持。
條件或說法不符回證據條件或只修該頁稿，重查內容讓錯誤在渲染前停止，減少重排整份投影片。
連結、互動或版面失敗回渲染或局部調整逐頁稿，再跑瀏覽驗收只修發生問題的頁面或互動。

本次由 Codex 依 Graph 調度各節點，腳本檢查引用、已知條件與瀏覽行為。預設每個退回節點最多修兩輪。若仍缺支持，就暫停該說法並列出缺口。內容與瀏覽檢查都通過後交付。

一次實跑的檢查紀錄

此次重跑最後一篇來源的收件時間為 2026-11-17T15:24:57.010+08:00（臺灣時間），即 2026-11-17T07:24:57.010+00:00（UTC）。

初版 Chrome 紀錄的臺灣時間是 11 月 17 日 02:59:53，換算 UTC 是 11 月 16 日 18:59:53。初版來源日期曾由程式固定填入，本次改由程式在收到每個 HTTP 回應時記時，並重算完整快照的指紋。Chrome 也已重跑並使用此次實測紀錄。

海報情境的 HTTP 實測

用本機測試伺服器與 Chrome 載入同一張圖片，為縮短測試時間設定 max-age=2。伺服器記錄到首次 200 並送出 69 位元組圖片，期限內再次載入時沒有收到圖片請求。過期後帶上 If-None-Match: "poster-v1"，版本相同時回 304，傳送的圖片內容為 0 位元組。換版後回 200、新 ETag 與新版圖片。

反思

哪一節最容易出錯？

這次以逐頁稿最多，共兩處。寫成簡短教學句時，手動重新整理和 ETag 存在與否這兩個條件被省略或混用。讀者照著操作時，可能看到和預期不同的請求。

檢查移到哪裡？

從逐頁稿的事後對照，前移到「查詢 Wiki」之後、「產生逐頁稿」之前的大綱證據關卡。先從條目抄錄前提給撰稿節點，再用同一批證據驗稿。

Graph 有什麼變更？

在查詢與逐頁稿之間新增「檢查大綱條件」。前提不清就回查概念頁，有可用證據才重寫受影響的頁面。本次只需更動第 3、4 頁的稿件。
